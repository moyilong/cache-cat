# CESP协议
## 为什么设计新的协议
RESP协议无法满足一些需求。
1. RESP无法存在队头阻塞问题，这个问题在Redis中被巧妙地消除掉了。这是因为Redis中命令本身就是串行执行的。并且每个命令的执行成本都是相似的。但是在Cache-cat中如果依旧按照流水线设计就会存在问题。在raft中读请求可以使用租约读等方式，读请求不需要进行一次完整的共识算法，因此大部分情况下不希望读写请求相互阻塞。该问题可以通过给每个请求增加请求id来解决这个问题。并且要在客户端和服务端都重新进行适配。
2. Redis默认情况下读请求，并不能手动设置读取的节点以及读取的模式。比如强制租约读或者read index等读取方式。理论上可以给RESP增加新命令来解决这个问题。
3. 无法动态感知集群的状态。只能通过兼容redis的哨兵相关的命令，来实现集群高可用。但是哨兵相关的命令，以及redis目前各个客户端的故障转移机制，并不契合RAFT算法的语义。redis的哨兵是去中心化的。

综上所述，Cache-cat决定开发自己的协议。来解决以上问题。协议名称定义为CESP（CachEcat Serialization Protocol）。
这里不在原来的Redis操作语义上进行任何修改，也不增加额外的符合RESP协议但在Redis中没有出现的新命令。所有新功能被放到新协议中。后续新协议会适配所有主流语言。
该协议不兼容老版本的RESP协议。并且完全使用新的端口处理请求。
## 协议编码
该协议大部分语义仍然保持和成熟的RESP3协议一致。这里在原始RESP头部定义了额外的固定的`@`作为开头。然后是32位也就是4byte的请求id。 如果发送的是读请求，则默认使用租约读。
如果使用`^`开头，则其后第一个byte表示读取的级别。0表示租约读，1表示read index，2表示允许任何形式的读取（允许在从节点上进行读取）。后面的4个byte依然表示请求id。`[@][读取模式][请求id][原始RESP协议的其余部分]`
返回时统一使用@作为开头，然后是32位的请求id号。
